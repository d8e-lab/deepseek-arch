> 状态：**已与用户逐条确认（2026-09-14）；阶段 A/B/C1 已实现并测试通过**（缺陷清单见 §4）
> 关系：本文只记录**相对 v2 实现（`da2ab9f`）的改变与未决项**；v2 的完整设计仍见 `plan/memory-heartbeat-design.md`。

## 0. 一句话总览

把记忆从"**每轮扫全部文件、索引只是影子、用户可手改**"改成"**harness 内存里维护一份总表作为工作集，模型只看投影，用户只读，改动以可见性变化的形式增量通知**"。
同时删掉到期提醒，并修掉评审发现的若干静默失效。

## 1. 已确认决策

### 1.1 存储与所有权

| # | 决策 | 说明 |
|:-:|:--|:--|
| D1 | **删除"到期提醒"（remindAt）** ✅已实现 | 移除字段、到期检查、注入块、写入工具参数、界面回调、相关测试；信号 D 退化为普通记忆；挂起项 C3 作废。附带收益：每轮全量扫描从 6 遍降到 4 遍 |
| D2 | **用户只读，agent/harness 自主维护** | 暂不支持用户手动编辑记忆文件，避免外部编辑带来的漂移与合并问题 |
| D3 | **每层一份机器可读总表，作为 harness 工作集** ✅已实现 | 内容 = 元数据 + 使用统计 + 状态（+ 可选的提醒信息，当前已随 D1 删除）。启动载入内存，会话内就地维护；模型只看由它渲染出的"一行简介"投影 |
| D4 | **正文留在主题文件，frontmatter 保留** ✅已实现 | 归纳代理写入时**同步维护**主题文件 frontmatter 与总表（两份真相的同步规则需实现时明确，见 §3 O1）；是否优化"两份真相"后续再议 |

### 1.2 会话内的判定与通知

| # | 决策 | 说明 |
|:-:|:--|:--|
| D5 | **会话内允许升级，也允许降级** ✅已实现 | 显式/判定型降级（写入 confidence 1、用户要求删除、判定过时）会话内立即生效 |
| D6 | **容量/老化驱动的降级与销毁仍在检查点** ✅已实现 | 窗口换出、容量淘汰、闲置降级、文件销毁只在 start（含 resume）/ compact / 按天 / 手动 gc 执行；exit 只做在途写入 flush |
| D7 | **通知按"是否在可见清单内"触发，不按更新时间** ✅已实现 | 进入可见（新增 / 升档跨过门槛）→ "新增/升级" + 一行简介；离开可见（降为 1 / 被取代 / 用户要求删除）→ "已退出清单/已删除"提示；仅可见范围内升降（如 3→2）不单独通知 |
| D8 | **增量清单不动已有部分** | 系统提示里的清单会话内不重写（避免前缀缓存失效），变化只以落盘的一条消息通知；compact / `/memory refresh` 时才重建 |

> D7 是必要修复：清单是冻结的，不通知"已删除"会让模型继续把一条已失效的偏好当现状。

### 1.3 边界与安全

| # | 决策 | 说明 |
|:-:|:--|:--|
| D9 | **`memory_read` 仅限项目/全局 memory 目录** | 去掉绝对路径/任意路径支持；配合召回给出的文件名，读路径不可能越界 |
| D10 | **整文件 64K 上限（含 frontmatter）** | 超限截断返回并带明确标记；**读取和写入两侧**都要在 TUI 给提示（写入侧兜底，最好让归纳代理一开始就不写超） |
| D11 | **置信度做字符串容错** | 模型常把 `"1"` 当字符串输出，现在会被静默丢弃，导致"软化删除"没生效却报成功；改为 `Number()` + 有限性校验 + 仍限 1–3 |
| D12 | **召回从总表选取** | 不做"只看文件名"的降级版本；总表已含 slug + 描述 + 置信度 + 标签，选取零扫描 |
| D13 | **加 workspace 级写锁** | 即使暂不支持多会话，仍有 TUI 与 cron `chat --prompt` 并发的可能；锁文件放 runtime 目录，保证同一 workspace 同一时刻一个写者 |
| D14 | **`chat --prompt` 强制搭配 `--workspace`** | 当前 `--workspace` 可选、缺省落到进程 cwd；对 cron/心跳不可控（会读写错误的项目层记忆与 runtime 目录）。缺失时直接报错退出，并修正选项描述 |

## 3. 仍未解决 / 待设计

**O1｜两份真相的同步规则（D4 的落地）**
总表与主题文件 frontmatter 会出现不一致（写入顺序、崩溃点、谁为准）。实现时需定：写顺序（建议正文/frontmatter 先、总表后）、崩溃后的修复路径（启动重扫校准）、以及"总表为准还是文件为准"。用户暂定"先记录，后续再议优化"。

**O2｜并发细节（D13 的落地）**
锁的粒度（整层 / 单条）、持有时长、超时与死锁处理；cron 唤起与 TUI 的抢占语义。

**O3｜自动升到最高档的封顶**
当前"被写两次"即可自动升到 conf 3，而 conf 3 会被 `memory_forget` 拒绝删除（等于获得删除豁免）。建议自动晋升封顶在次高档，待确认。

**O4｜使用统计缺字段的健壮性**
状态文件是未校验 JSON；若某条缺 `lastUsedAt`，时间解析会得到 NaN，可能静默冻结其老化。当前无写入者会产出这种数据，但建议加载时做校验与回退。

**O5｜真正会失败用例的测试缺口（跨 memory/subagent）**
现有"失败子代理"测试实际上没有制造失败（状态改由循环显式返回后，纯文本 `Error:` 被视为成功）。子代理侧的失败链路（见 §4）需要能真正抛错的用例。

## 4.1 阶段 C2/C3/C4 实现要点（2026-09-14）

- **总表 `manifest.json`（每层一份）**：`{version, updatedAt, activeDayCount, lastActiveDate, entries[元数据], usage}`；
  条目正文仍留在 `<slug>.md`（工作集里只存元数据，读全文才按需读文件）。
  `MEMORY.md` / `candidates.md` 仍是渲染视图，保持不变。
- **工作集生命周期**：首次使用/缺失/损坏 → 全量扫描重建并**自愈**写回；之后读走内存；
  写操作就地更新 + `flush` 落盘；`dirty` 期间禁止从磁盘重载（避免丢掉本进程刚写的条目）；
  其它进程写入通过 manifest 的 mtime 检测并重载（TUI + cron 并发可见）。
- **旧 `state.json`**：仅在重建时一次性导入（usage/活动日），此后不再写入。
- **会话内局部判定**：`recordUse` 达阈值即升级、conf 0 被任何触达即复活（`recordTouch` 只复活不升级）；
  **写路径不触发升级**（否则"显式降到 1"会被同一次写入抬回）；
  空闲降级/窗口换出/容量淘汰/销毁仍只在检查点结算。
- **可见性变化通知**：版本键 = `updated|confidence`；升级报 `updated`（带新 confidence），
  离开可见清单报 `removed/retired`。
