# Frontend Componentization — 前端组件化设计理念

> 目标：把命令式单体 UI 重构为"组合根 + 独立组件"结构，使每个界面块可独立测试、独立复用、正交修改。

---

## 核心理念

界面不是"一个大类里的一串方法"，而是"一个组合根 + 一组组件"：

- **组合根**：只保留应用状态机、命令语义、事件编排与组件接线
- **组件**：每个界面块是独立类，自带状态、渲染与输入处理，可单独实例化、单独测试
- **拼装**：组件通过注入依赖与回调组装，不直接互相引用内部实现

## 分层原则

```
无 I/O 纯计算层（零件）   ← 输入数据 + 尺寸 → 输出行数组/字符串，零 process.* 引用
有状态组件层（积木）      ← 持状态、渲染到注入的输出通道、暴露输入处理
组合根（拼装）            ← 状态机 + 组装接线，不承载组件内部逻辑
```

依赖方向单向：组合根 → 组件 → 纯计算层。低层不反向依赖高层，纯计算层不被任何 I/O 污染。

## 组件边界判定

以代码证据划分边界，而非凭感觉：

- 一组**内聚的状态字段 + 渲染方法 + 输入处理方法**，且与组合根其他职责无交叉引用，即可抽为一个组件
- 组件应能回答"我画什么、我多高、我如何处理按键"，不回答"我在屏幕哪里"（位置由容器/组合根负责）
- 边界是否成立的可测判据：能否用假数据独立实例化并驱动渲染/输入，而不触碰组合根的其他部分

## 统一契约

组件暴露一致的生命周期与能力，组合根只依赖契约不依赖实现：

- 渲染：把当前状态渲染到注入的输出通道
- 输入：处理按键/数据，返回是否已消费
- 清理：释放定时器等资源
- 数据源：通过窄接口注入（如"取列表"“发送消息”），组件不直接依赖业务门面类

## 重复抽象下沉

用"同一把尺子"审视所有组件：**凡是出现 ≥2 次的实现细节，下沉为共享抽象**，而不是各写一份。

常见重复源：可滚动高亮列表渲染、滚动状态机（clamp/翻页/跟随末尾）、按键序列解析、视口行渲染循环、富文本（如 markdown）段落渲染、光标/清屏序列。

下沉目标是纯计算层，使每个抽象可独立单测；消费方组件退化为薄壳，只负责"从哪拿数据、调哪个抽象"。

## 刻意不抽清单

组件化不等于无限拆分，以下情况**不抽**，避免过度设计：

- 一次性输出片段（如页眉、分隔线、瞬时提示）
- 结构差异大、共享收益低的表面相似视图（基类会引入空 hook）
- 散落面广但语义各异的底层序列迁移（收益低风险高）

## 行为不变验证

纯内部重构的硬性要求是**用户可见行为 100% 不变**：

- 先明确"不做什么"（不引入布局引擎、不改变视觉、不新增功能）
- 重构前已有回归测试是安全网；抽取后测试下沉为组件级（直接实例化组件），断言等价保留
- 每一步独立可编译可测试，先跑通再继续
